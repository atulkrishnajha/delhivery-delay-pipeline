## How to run
To reproduce this project from a clean clone, open your terminal and run the following commands in exact order:
1. `pip install -r requirements.txt` (This installs the exact library versions required).
2. `python3 generate_data.py` (Generates the raw data).
3. `python3 part_a_clean_eda.py` (Cleans data and generates EDA reports).
4. `python3 part_b_regression.py` (Trains and evaluates regression models).
5. `python3 part_c_classification.py` (Trains and evaluates classification models).
6. `python3 part_d_segments.py` (Clusters hubs into business segments).
7. `python3 package_model.py` (Saves the final model and metadata).
8. `python3 predict_delay.py` (Scores new shipments and outputs actionable lists).

*Note: `models/delay_model.pkl` is dynamically regenerated by running `python package_model.py`. The committed pickle file loads reliably only on the specific scikit-learn version pinned in `requirements.txt`.*

## Data findings
Based on the historical data analysis (`part_a_delay_by_group.csv` and `part_a_correlations.csv`):
* **Service Type:** The `Express` service is delayed most often, failing at a rate of `0.4897`.
* **Hub Tiers:** As we move from Tier 1 to Tier 3 hubs, the delay rate severely worsens, jumping from `0.04` in Tier 1 to `0.44` in Tier 3.
* **Distance:** Delays scale drastically with distance. Parcels traveling 0-200km have a delay rate of only `0.0219`, while those traveling 601+ km fail `0.8523` of the time.
* **Correlations:** The three variables most strongly correlated with actual delivery hours are:
  1. `promised_hours`: `0.8372`
  2. `distance_km`: `0.4011`
  3. `n_stops`: `0.2458`
* **Log Transformation:** The `declared_value_inr` was log-transformed because the data is highly right-skewed. Before the transform, the mean (`1533.0542`) was vastly higher than the median (`1121.5`), , whereas log_declared_value has a mean of 7.0280 and a median of 7.0220, restoring a normal distribution for linear models.

## Model results (regression)
* **Baseline:** The mean baseline achieved an R² of `-0.0211`. Because it is negative, it means a naive average guess is actually worse than predicting a horizontal line; our ML models must beat this to be viable.
* **Winning Model:** The `linear_regression` won the validation phase and achieved a final Test RMSE of `4.5235` hours.
* **Bias vs. Variance (Tree Depth):** At Depth 1, both training and validation RMSE are extremely high (a gap of only `0.499`), proving High Bias (underfitting). At Unlimited depth, the model memorizes the training data perfectly (Train RMSE = 0) but fails on validation, causing a massive gap of `7.8368`, proving High Variance (overfitting).
* **Learning Rate:** For Gradient Boosting, a rate of 0.1 was optimal. A rate of 0.01 is too slow (the 100 trees can't reach the answer in time), and 1.0 is too aggressive, causing the algorithm to wildly overshoot the mathematical minimum.
* **Cross-Validation:** * "Although linear_regression won on the single validation split, gradient_boosting won in Cross-Validation. I would ship gradient_boosting, as Cross-Validation tests across 5 different slices of data, proving it generalizes better to unseen data."*

## Model results (classification)
* **Blind Baseline:** A model that blindly guesses "On-Time" for everything achieves an accuracy of `0.7667` because ~77% of parcels are on time. However, it is entirely useless because its Recall is 0—it catches exactly zero delayed parcels.
* **Noise Columns:** The 5 noise columns accounted for a combined `0.2253` share of the forest's importance. Thankfully, SelectKBest properly identified all 5 as having zero signal; they all ranked 8th or lower by F-score.
* **SelectK Results:** The `k` table shows that restricting the model to the top 7 features maintains (and often improves) the Validation F1 score, proving that dropping noise prevents the model from hallucinating false patterns.
* **Tuning:** `No`. Tuning on a tiny 180-row validation set can sometimes result in overfitting to that specific validation slice rather than finding universally better parameters. 
* **The Threshold:** To meet the Operations Rule (Recall >= 0.80), the threshold was lowered to `0.5`. Lowering the threshold intentionally sacrifices Precision (increasing false alarms) to maximize Recall (catching actual delays). 
* **Test Performance:** On the final Test set, the model achieved a Precision of '0.6889' a Recall of `0.7561`, and an F1 of `0.7209`. Comparing this to the validation recall requires honesty: the test set only contains 41 actual delayed parcels, meaning one or two lucky/unlucky guesses heavily swing the percentage.

## Production plan
* **Production-Readiness Mappings:**
  1. *Consistency:* Achieved by keeping all cleaning and feature engineering inside `src/shipment_prep.py`, which is shared identically by both the training and prediction scripts.
  2. *Reproducibility:* Guaranteed by pinning exact versions in `requirements.txt` and hardcoding `random_state=42` across all splits and algorithms.
  3. *Maintainability:* Code is broken into modular scripts (`part_a`, `part_b`, etc.) rather than one giant spaghetti file.
  4. *Reliability:* `package_model.py` saves fallback median values so the live scoring script doesn't crash if a scale goes offline and returns a missing weight.
  5. *Monitorability:* The `part_d_reload_check.csv` automatically verifies that the saved model behaves identically to the trained model before deployment.
* **Monitoring Triggers:**
  1. *Weekly Delay Rate:* Trigger an alert if the global share of delayed parcels rises above 28%.
  2. *Flag Volume:* Trigger an alert if > 35% of daily parcels are flagged, potentially indicating our threshold needs adjustment.
  3. *Live Recall Check:* Once parcels are actually delivered, calculate the real recall. Trigger retraining if live recall drops below 0.75.
* **Retraining & Data Drift:** The model should be retrained quarterly. The September `sale_event_flag` cannot be compared to normal weeks; it must only be benchmarked against similar peak events (e.g., Diwali sales). Data drift would appear as gradual shifts in inputs, such as the median distance increasing as the company expands to rural areas, causing our scaler to become outdated.

## Limitations
1. **Synthetic Data:** The model is trained on synthetic data generator outputs. Real-world logistics data contains much messier edge cases (e.g., destroyed barcodes, vehicle breakdowns).
2. **Small Test Set:** The test set for classification only contained 41 delayed parcels. A test set this small means a change of just 2-3 parcels creates a massive swing in Recall metrics.
3. **Threshold Tuning:** The threshold was tuned on a single 180-row validation split. A robust production system would tune the threshold using Cross-Validation to ensure it holds up against data variance.
