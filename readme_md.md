# Delhivery Last-Mile Delay Intelligence Pipeline

**Author:** ATUL KRISHNA JHA 

## Project Overview
This project is an end-to-end machine learning pipeline designed to predict shipment delays for Delhivery. By analyzing historical delivery data, the model identifies patterns that lead to delays, helping optimize logistics and improve customer satisfaction. It answers three core operational questions: exact delivery hour estimates (Regression), binary delay predictions (Classification), and hub performance segmentation (Clustering).

## Tech Stack
- **Language:** Python 3
- **Machine Learning:** Scikit-learn (RandomForestClassifier, GradientBoostingRegressor, GridSearchCV, KFold, KMeans)
- **Data Manipulation:** Pandas, NumPy
- **Serialization:** Joblib

## Project Structure
- `generate_data.py`: Script used to generate the initial raw shipment dataset.
- `src/`: Core directory containing the pipeline logic.
  * `__init__.py`: Marks the folder as a standard Python package.
  * `shipment_prep.py`: Contains the data preprocessing logic, constants, and feature engineering steps required before model training.
- `part_a_clean_eda.py`: Cleans raw data and generates exploratory data analysis.
- `part_b_regression.py`: Regression modeling for delivery hours.
- `part_c_classification.py`: Classification modeling for delay probability.
- `part_d_segments.py`: K-Means clustering for hub operations.
- `package_model.py`: Serializes the final pipeline for production.
- `predict_delay.py`: The final scoring script for new incoming parcels.

## How to run
To reproduce this project from a clean clone, open your terminal and run the following commands in exact order:
1. `pip install -r requirements.txt` (This installs the exact library versions required).
2. `python generate_data.py` (Generates the raw data).
3. `python part_a_clean_eda.py` (Cleans data and generates EDA reports).
4. `python part_b_regression.py` (Trains and evaluates regression models).
5. `python part_c_classification.py` (Trains and evaluates classification models).
6. `python part_d_segments.py` (Clusters hubs into business segments).
7. `python package_model.py` (Saves the final model and metadata).
8. `python predict_delay.py` (Scores new shipments and outputs actionable lists).

*Note: `models/delay_model.pkl` is dynamically regenerated by running `python package_model.py`. The committed pickle file loads reliably only on the specific scikit-learn version pinned in `requirements.txt`.*

## Production plan
* **Production-Readiness Mappings:**
  1. *Consistency:* Achieved by keeping all cleaning and feature engineering inside `src/shipment_prep.py`, which is shared identically by both the training and prediction scripts.
  2. *Reproducibility:* Guaranteed by pinning exact versions in `requirements.txt` and hardcoding `random_state=42` across all splits and algorithms.
  3. *Maintainability:* Code is broken into modular scripts (`part_a`, `part_b`, etc.) rather than one giant spaghetti file.
  4. *Reliability:* `package_model.py` saves fallback median values so the live scoring script doesn't crash if a scale goes offline and returns a missing weight.
  5. *Monitorability:* The `part_d_reload_check.csv` automatically verifies that the saved model behaves identically to the trained model before deployment.
* **Monitoring Triggers:**
  1. *Weekly Delay Rate:* Trigger an alert if the global share of delayed parcels rises above 28%.
  2. *Flag Volume:* Trigger an alert if > 35% of daily parcels are flagged, potentially indicating our threshold needs adjustment.
  3. *Live Recall Check:* Once parcels are actually delivered, calculate the real recall. Trigger retraining if live recall drops below 0.75.
* **Retraining & Data Drift:** The model should be retrained quarterly. The September `sale_event_flag` cannot be compared to normal weeks; it must only be benchmarked against similar peak events (e.g., Diwali sales). Data drift would appear as gradual shifts in inputs, such as the median distance increasing as the company expands to rural areas, causing our scaler to become outdated.

## Limitations
1. **Synthetic Data:** The model is trained on synthetic data generator outputs. Real-world logistics data contains much messier edge cases (e.g., destroyed barcodes, vehicle breakdowns).
2. **Small Test Set:** The test set for classification only contained 41 delayed parcels. A test set this small means a change of just 2-3 parcels creates a massive swing in Recall metrics.
3. **Threshold Tuning:** The threshold was tuned on a single 180-row validation split. A robust production system would tune the threshold using Cross-Validation to ensure it holds up against data variance.
